## What happened to the v1 jobs

- **`xltwpkg-py312-v1` (image python:3.12, run 11:40-12:17 UTC).** Setup passed (helpers fetched, the
  pre-registration public and identical, XLTW-Test extracted, wheels resolved and fetched). `bash build.sh --offline`
  passed with the network off, but it printed `using /usr/bin/python3.13 (cp313)`: the image carries Debian's
  Python 3.13 next to its default `/usr/local/bin/python3` (3.12), and build.sh 0.1.0 tried `python3.13` first. It
  unpacked the cp313 wheels and its own import check passed under 3.13. The unit tests then ran under 3.12, and the
  two tests that import `lib/` in a subprocess (`test_lib_has_the_pins`, `test_pyvrp_logger_goes_to_stderr`) used
  the test runner's interpreter: numpy's cp313 extension cannot load in 3.12 (`No module named
  'numpy._core._multiarray_umath'`). 18 of 20 tests passed, including both watchdog tests. The job stops at the first
  failed step, so `conformance.py` never ran. **C0-C6 were not scored.** This was a fault in the package and its
  tests (two interpreters assumed to be one), not in the solver.
- **`xltwpkg-py311-v1` (image python:3.11).** The setup step could not resolve `galgos.inf.puc-rio.br` ("Temporary
  failure in name resolution") when it went to download the XLTW-Test archive, and gave up after one try. Nothing
  was built or run. Not scored.
- **`xltwpkg-n8575-v1`** was still queued and would have failed the same way as py312. It is replaced by v2.

## What changed (package 0.1.1; `solver.py` is byte-for-byte the same)

- `build.sh` tries `XLTW_PYTHON`, then the default `python3`, then `python`, and only then `python3.13`, `3.12`,
  `3.11` (CPython only).
- `lock.py --install` refuses a `--tag` that is not the running interpreter's, and records that interpreter
  (`executable`) in `lib/XLTW_BUILD.json`. Downloads are retried up to three times.
- `test_pkg.py` runs every subprocess that imports `lib/` under the recorded interpreter, checks that `./solver`
  execs it, and has a new test for the tag check (21 tests).
- `conformance.py` re-runs itself under the recorded interpreter if it was started under another one, and records
  both in `results.json`.
- `fetch_helpers.py` retries downloads, and checks that `expectations.md` on `main` still has the SHA-256 the v1 jobs
  recorded (296c734b...) and that this addendum is public and identical to the job's copy before anything runs.

## One more case for the watchdog, seen after the pre-registration

The baseline's part b3 run (`xltwrun-b3-v1`, finished 06:43 UTC) had a second stuck call of the same kind:
**XLTW-Test-n10001** (10,000 customers, capacity-bound, K = 260) printed its last solution at 592.95 s, did not
stop by itself before its 600 s limit, got SIGTERM on time (600.09 s) and was SIGKILLed 5 s later. Unlike n8575,
this one is not capacity-free, and it was still printing solutions 7 s before the limit. It ran at least 7.8 s
past the solver's own stopping point (597.3 s) before it was killed; how much longer it would have run is unknown. The
watchdog's hard deadline (598.65 s there) would have ended it. It is not part of C7/C8; it is noted here so the
second case is on record before any v2 result is known.
