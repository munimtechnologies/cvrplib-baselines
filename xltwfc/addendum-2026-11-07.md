`expectations.md` (commit d19acfd) is unchanged: same question, same instances, seed, limits and harness, and the
same predictions S0-S5, with the same thresholds. This addendum records a crash, its fix, and one change to the
re-run rule. All of it is written before any of the study runs F1-F4.

## What happened

Both jobs (`xltwfc-a-v1` from 02:59 UTC and `xltwfc-b-v1` from 03:03 UTC on 2026-11-07) built the package offline, passed
the package's unit tests and this study's 11 unit tests, and then stopped in the 40 s smoke run on XLTW-Test-n1048,
as designed: the smoke gate refuses to start the study unless the fixed-cost solve ran. The solver crashed at the
start of the fixed-cost solve:

    AttributeError: 'pyvrp._pyvrp.Route' object has no attribute 'visits'

`fcsolver.py` 0.1.0-fc1 built the starting solution with `Route.visits()`, which PyVRP 0.14.1 does not have. The
unit tests did not catch it because none of them ran PyVRP. The crash came after the first feasible solution had
been printed, so the smoke run's stdout held a valid solution (38 vehicles, distance 78,665), but the process
exited 1 and the fixed-cost phase never ran. n1048 is the smoke instance only, not one of F1-F4; no study run
happened, and no study result was seen.

## The fix (fcsolver.py 0.1.0-fc2)

`visits()` now converts routes exactly as the package's own distance phase does (`solver.py` at commit 19c7eb6:
`[[c - 1 for c in r] for r in solution_routes(best)]`, which the package's conformance runs have exercised).
Nothing else in the method changes: same first solve, same F = 10 x ceil(d0 / k0), same stop rule, same distance
phase.

Two tests are added: one checks `visits()` against the package's conversion, and an end-to-end test runs
`fcsolver.py` under the package's interpreter on a synthetic 80-customer instance for 12 s and requires exit 0,
clean stdout ending in a `Cost` line, the stats line, and (when the first solution is above the bound) at least
one iteration of the fixed-cost solve.

## One rule change: frozen runs

`expectations.md` says a frozen run (harness poll gap above 1 s) is re-run once, and a frozen re-run means no valid
run. Our host pauses containers when its memory runs low, and in `xltwfull/` the same instance (F2) froze twice,
which failed that study's gate for a reason unrelated to the solver. From this addendum on, a frozen run is re-run,
unchanged, until it is not frozen, **at most 3 attempts in all**; every frozen attempt is kept in the results
(`frozen_tries`) and counted in `attempts`. The smoke run follows the same rule. Before scoring, every counted run
is also checked against the host's pause log (pauses that end within the 1 s poll window cannot be seen by the
harness), and any counted run that overlaps a logged pause is reported.
